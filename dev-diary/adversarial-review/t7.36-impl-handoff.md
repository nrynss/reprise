## What was built

The host stem is written on the context clock. `HostStemWriter` stores each
reply at the span the player reports, with silence from a shared origin, and
it cuts an interrupted reply at the flush. The writer is armed when the
audio context opens, before any host audio, so the greeting is on that clock
too.

The first user block is preceded by silence back to that same origin when
the block starts later. Every later captured block is appended once, in
order. `publishUserBlock` does not drop a block and does not append one
twice. `sendAudio` can refuse a block before the socket is open or after the
end, and that refusal does not touch the stem.

The socket reports the provider id once, as soon as it learns it. That early
post stays, because a crashed or suspended page sends no close at all. Both
`SessionGuard` calls pass a `body` function. The guard reads it at send time,
so an id learned after `attach` is included. The body is the string
`{"provider_session_id":"<id>"}`. An empty id still leaves a stored id in
place.

`beforeunload` and `pagehide` both send the provider end. The socket latches
a send that lands. A send that throws clears the latch, so the later event
can try once. The beacon still carries the id.

`@nrynss/chaaya` is pinned to `0.2.1` exactly in `web/package.json` and
`web/package-lock.json`. The stack table in `README.md` names that pin. The
planning copies of the pin were left for landing.

Voice unit tests were run with Vitest from `web/`. Nine files passed, 85
tests, including the host stem marks, the beacon body, the keepalive
fallback, and a retry after a thrown end send.

## What surprised us

The greeting used to be appended raw, before the writer existed. Later
silence then counted that same interval again, so every reply after the
greeting sat late. The writer now exists first.

The 20 to 60 ms steps between the user stem and the provider recording are
not explained by a dropped or repeated block on this path. I read
`publishUserBlock` and did not measure the steps.

Firefox kept the call open about 30 seconds because a bare socket close
starts the provider resume window. `pagehide` already sent `session.end`,
and the beacon did run, because the end rows existed with an empty provider
id. Chrome delivered `session.end` and ended at once. `settleOnEnd` in
`cmd/reprise/main.go` starts a reconcile job. That job reads duration and
settles money. It does not send `session.end`. `DELETE` does not end a
connected socket. The probe is `dev-diary/probes/voice-agent.md`, and
`TerminateSession` in `internal/assemblyai/terminate.go` says the same. Those
paths own a server-side end, and none of them can end the live socket.
Firefox also cancels a keepalive fetch from `pagehide`, while `sendBeacon`
still goes out. The new `beforeunload` send is the client attempt to put
`session.end` on the wire while the socket can still take it. I did not edit
the server files.

`web/src/routes/record/mock-session.spec.ts` expects host bytes of
`2 * 48000 * 2`, which is both tones in full. A reply cut before it plays is
shorter. That spec is outside this task's owns. I did not edit it and I did
not run it.

`npm install` dropped an extraneous `yaml` entry from the lockfile. It was
not a dependency of the app.

`./tools/check.sh` failed before tests. ffmpeg is 9.0.2, not the pinned
9.0.1. I did not change `tools/check.sh`.
