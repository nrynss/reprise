## What was built

`EndSession` writes `{"type":"session.end"}` on a live voice socket, then
deletes the provider record. A socket that is already closed still
deletes. It does not open a replacement. A second end does not open a
new socket.

When this process already holds the socket, the frame goes on that
socket. Nothing else is dialed.

When it holds none, one dial opens a voice websocket on the sessions
host. The first frame is `{"type":"session.resume","session_id":"..."}`.
After `session.ready`, that same socket gets `session.end`. The dial
never sends `session.update`, so a refused resume cannot start a fresh
call. `session.end` is still the end frame. It has to ride a socket that
already holds the session.

The sweep calls that end after the settle and stores whether the frame
was written. Reconcile uses the same end after the recording and the
timeline are stored. An open read stops the socket first and reads once
more, so the delete does not run before a duration exists.

A refused dial returns an error and does not delete. A host that does
not upgrade counts as a gone socket, and the delete still runs.

Money still settles once. A second reconcile stores nothing new.

## What surprised us

The server never holds the browser socket. The only measured end is
`session.end` on the voice websocket. DELETE returns 204 and leaves a
connected socket billable. That is already in the voice probe.

A tab close whose frame never leaves usually drops the socket and starts
the 30 second resume window. Resume, then `session.end`, is how this
process reaches that window. A socket that is still connected cannot
take a frame from here. Resume is for after the disconnect. If resume
is refused, the delete still runs, and a connected socket can stay
billable.
