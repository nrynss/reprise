## Findings

### 1. Mark done while the render slot is busy fails the episode for good

| Column | Value |
|---|---|
| Severity | H |
| Where | `internal/episode/done.go:35` (`RequestRender` calls `Fail` on any start error), with `cmd/reprise/finish.go:81` (`StartEpisodeKind` passes `job.ErrLimit` through) and `internal/api/episodes.go:434` |
| What | The render kind runs one job at a time, and Keel refuses a second start with `job.ErrLimit`. So a mark done that arrives while any other render runs fails its episode. That covers two guests marking done together, and a mark done during a render that the boot resumed or that `startWaitingRenders` started for a stuck episode. The API answers 429 with "retry this episode". But no route retries. `episode.Retry` has no caller, and mark done accepts only a draft. So the episode stays `failed` with its stems stored and never ships, against the always-ships invariant. The new walk cannot rescue it, because it lists only `rendering` episodes. The live URL can hit this whenever two visitors finish close together, and the owner can hit it right after a deploy while the stuck backlog renders. The demo video, recorded alone, survives it. |
| Pin | `TestProbeMarkDoneWhileRenderBusyStillShips` in `dev-diary/probes/t7.29-rev-r2/busy_render_probe_test.go`. Guest A's render holds the slot. Guest B marks done through the routes. The probe then frees the slot and ticks `advanceAll` until both ship. At the hash it fails at once: "mark done while the render slot was busy answered 429 and left the episode failed". With the throwaway fix above it passes, with one render job per episode. |
| Mutation | Once the fix is in (a refused render start leaves the episode `rendering` for the walk to start), restore the `Fail` on `job.ErrLimit`. For the throwaway fix, that means deleting the `if errors.Is(err, job.ErrLimit) { return "", nil }` branch. The probe then fails again. |
