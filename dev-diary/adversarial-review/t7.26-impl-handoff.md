# Implementer handoff: raw PCM stem uploads

## What was built

`cmd/reprise/main.go` now accepts `audio/pcm` in the closed upload
content type set, and headerless signed 16 bit mono takes convert to
headed WAV from the sample rate the completion stored per stem row.
`cmd/reprise/pcm_stems_test.go` pins the four behaviors with real
files, the real upload handler, and real ffprobe.

## Conversion design and where the header is built

The header is built in exactly one builder, `wavFromMonoPCM`, and it
reaches the bytes through three paths.

1. Eager convert on link. `stemsComplete.ServeHTTP` calls
   `convertRawStems` right after `CompleteStems` succeeds. It reads the
   linked stem rows with their stored rates and rewrites any headerless
   stem file to WAV in place, keeping the file mode. WAV files pass
   through untouched.
2. Locate converts for render. `pipeline.locateStems` now reads rates
   beside ids and offsets through `linkedStemFiles`, and calls
   `ensureWAVInPlace` before returning each path. The render resolver
   uses this locate function, so renders always read headed audio.
3. Resilient read in `editInputs`. Bytes read from disk pass through
   `headedStemAudio`, which heads raw bytes in memory from the stored
   rate. When the on disk file was still raw, the duration probe runs
   through a temp WAV file (`probeHeadedAudio`) that leaves after. A
   crash between link and convert still converges on playable audio
   with the stored rate.

The WAV header is 44 bytes: RIFF, WAVE, one PCM fmt chunk (format 1,
1 channel, stored rate, byte rate of twice the rate, block align 2,
16 bits), and one data chunk with the raw length. Empty and odd length
raw refuse under one sentinel, and a non-positive or huge rate refuses
under another. The probe never reports zero silently. Existing WAV
stems never rewrite, because the RIFF WAVE sniff skips them.

## What surprised us

The upload open accepts any named content type. The allowlist refuses
at completion when the store persists, answering 415 with
`unsupported_type` and storing no blob. The unknown type pin therefore
drives open, one chunk, and complete, and asserts the refusal at
complete. The first draft of the pin asserted 415 at open and failed
with 201, which exposed this ordering.

## Contract change

None. No new spend path, no budget change, paid kinds untouched. The
completion response, the stem rows, and the job chain keep their
shapes. The only visible change is that `audio/pcm` uploads complete
instead of refusing, and stored stem files for such takes carry a WAV
header after link.
