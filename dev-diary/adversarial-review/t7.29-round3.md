## The queue design

- **202 `queued: true`.** Sound. `RequestRender` returns an empty id only when `WaitWhenBusy` is set and the start
  failed with `job.ErrLimit`. The handler derives `queued` from that id. The episode stays `rendering` with no render
  job, which is the exact set `startWaitingRenders` walks. The 429 `render_busy` answer now needs a service that does
  not wait, and the binary never builds one. The editor misreads this answer (finding 1).
- **Gallery poll.** A queued row reads its detail every fourth 500 ms tick, which is every 2 s, one read per queued
  row. It stops once the detail names a pass that is not queued, including a render that started, a failed episode
  or an analysing one. `teardown` clears the set. The poll is not bounded when the detail refuses. `followPass`
  returns before it touches `queued`, so a gone episode is polled every 2 s for as long as the page stays open
  (finding 4). There is no in-flight guard either. A detail slower than 2 s stacks reads, but the rate stays one read
  per row per 2 s, so I record no finding for that.
- **Second mark done answers 409.** Yes. `MarkDone` moves only a draft, so the repeat reads `rendering` and reports
  `ErrIllegalTransition`. `TestMarkDoneQueuesBehindABusyRender`, `TestRequestRenderWaitsWhenTheRenderSlotIsBusy`
  and the round 2 pin each check it, and each also checks that nothing else starts.
- **The new guards.**
  - The join that answers with a render that already moved the episode on is pinned by
    `TestRenderStartJoinsTheRenderThatShipped`. Restoring the old condition fails that test.
  - Replacing `Transition(rendering, failed)` with the old `Fail` leaves every suite green. I looked for a way to
    reach the case it guards and found none. A start error that is not `ErrLimit` comes from a diary read fault or
    a failed stamp. Under the lock, a failed stamp means no other render was found, so no racing render can have
    moved the episode on. The guard is correct and does no harm. It is unpinned but not a defect, so I record no
    finding.
- **Races.** Every render start runs under `schedMu`, reads the state and the newest render job first, and stamps
  before it releases the lock. That covers mark done, the walk and the boot resume. Mark done moves draft to
  rendering outside the lock, so the walk can start that render first, and mark done then joins it. A render that
  settles in that gap moves the episode on, and mark done then joins the finished render. `markRendered` holds the
  lock across its state check, and `advance` holds it across every pass start. I found no interleaving that makes
  two renders for one episode, or that reruns a paid pass. One behaviour is worth recording as a note, not a finding.
  The walk runs every 30 s, and the finishing render holds its slot until its work returns. So a queued render starts
  up to 30 s after the one ahead of it. A fresh mark done that lands in that window takes the slot first. That delays
  a queued episode but never loses it.
- **Restart with a queued episode.** `recoverRender` leaves an episode with no render job to the walk. `recoverFinish`
  then calls `advanceAll`, which starts the oldest waiting render. `TestEveryStuckRenderShipsOneAtATime` pins exactly
  that shape.
