## What it built

`internal/retention/` holds the sweep and the keep. Twelve Go tests pin
both sides through a real SQLite file, a real media store, and scripted
provider doubles.

* **Sweep** runs as the `retention-sweep` job kind, idempotent with a
  resume hook and five attempts. The job reads expiry fresh inside the
  run: guests of kind guest with last seen time before now minus the
  window. Owners never list, and a stamp exactly at the cutoff survives.
* Each expired guest erases episode by episode through the episode
  erasure service, so the targets are exactly the erase set: the episode
  row with its cascade, every grouped blob, the cover file, the provider
  session, and every remaining batch transcript with delete confirmation.
  Then the sweep removes stray uploads, the session rows, and the user
  row. Foreign keys force that order, so guests run sequentially.
* The sweep carries no request user, so the inner erasure trusts a
  per-run allowlist of the expired guests instead of a session. The
  allowlist resets every run from the guest list.
* The job snapshot records the cutoff with per-guest episode lists and
  inner erasure ids, published after every started and finished erasure.
  A resumed run unions unconfirmed guests with freshly expired ones and
  restarts stuck erasures from their recorded ids. `ReSweep` does the
  same for a failed sweep after a provider outage.
* **Keep** moves one episode to the keeping owner in one transaction:
  the episode row with the next free number, every content row beneath
  it, and every grouped blob. The provider copies stay named by their
  own ids and leave the sweep inventory with the episode. Keeping twice
  succeeds without renumbering.

## Pins, all offline

* An idle guest loses every content row, every media row and file, both
  covers, the user row, and the session rows. Its provider session ends
  and its transcripts read soft-deleted. A fresh guest keeps every row
  and file by count before and after.
* A kept episode keeps its rows, blobs, cover, and provider copies
  through the sweep that deletes the rest of its guest, including the
  guest user row. The keeper takes number one, or the next free number.
* A blocked provider delete holds the sweep while a fresh runner opens
  on the same ledger. Both runners converge after release, and the idle
  guest is gone with the fresh guest intact.
* A refused transcript delete fails the sweep with the episode rows
  gone. `ReSweep` after the outage finishes the transcripts, the rows,
  and the guest from the recorded ids.
* An unset window sweeps a ninety-one day idle guest and keeps an
  eighty-nine day one. A guest at the exact cutoff survives.

## What surprised it

* The episode erasure kind name is fixed, so a second eraser would
  steal its resume hook. The sweep therefore drives the existing
  erasure service instead of owning an eraser, with an allowlist
  standing in for the missing request user.
* The tests caught two real defects. The snapshot published only per
  guest, so a mid-guest failure lost the erasure ids and leaked provider
  copies. It now publishes after every started and finished erasure.
  Two resume attempts also raced on one stuck erasure, and the loser
  failed on already complete. It now reads complete as done.
* The resume test waited on the first seeded episode while the sweep
  erases in id order. It now waits on the guest episode count.
* Seeded rows owned by an expired guest sweep like any guest rows.
  Shared season rows belong to a non-guest owner and never list. If a
  per-guest seed copy ever exists, the sweep treats it as guest data
  and the seed flow re-creates it on the next visit.

## Contract changes for wiring

* Open with the diary handle, the media store, the cover directory,
  the provider clients, and the window, then open the runner with
  `Kinds()` registered and call `BindRunner`. `Sweep` answers the job
  id at once, and the caller follows it over the job stream. `ReSweep`
  takes a failed sweep job id and answers the retry job id.
* Call `Keep` with the episode and the keeper before expiry. No route
  exposes it yet. The keeper must already own a user row.
* A stuck sweep needs an operator control calling `ReSweep`, the way a
  stuck erasure needs one calling the re-erase. No route exposes it yet.
* Live remeasure is owed. Provider doubles stand in throughout. No
  library gap surfaced, so no issue was filed.
