## Verification notes, item by item

1. OIDC strictness. The header gate (`google.go:474`) refuses anything but
   `RS256` with a `kid`, and RSA verification (`google.go:495`) fails closed
   beneath it, so `none` and `HS256` tokens die twice. Audience accepts one
   string or a list (`google.go:248`) and must contain the client id
   (`google.go:509`). Issuer must echo exactly (`google.go:506`). Expiry
   uses `<=` with no skew (`google.go:519`), so a missing or boundary `exp`
   refuses. A missing nonce claim refuses (`google.go:522`, empty check
   first, then constant time compare). A missing subject refuses
   (`google.go:525`). Every refusal shares the one token sentinel, so no
   answer teaches which guard tripped. Probed each case above, all fail
   closed.
2. State, nonce, PKCE binding. The pending entry binds session and user
   (`google.go:548`), and cross-session completion returns `ErrGoogleState`
   before any provider call. State is single use on success
   (`googleForget` at `google.go:574`); replaying the callback URL meets an
   unknown state. The verifier never leaves the server (`google.go:359`),
   and a challenge mismatch refuses at the token endpoint (probed).
3. Identity key. Claims carry no address (`google.go:263`). The stored row
   is `google:<sub>` (`google.go:626`). Two distinct subjects attach two
   rows with no merge (probed). The same subject resolves to its holder.

   (`google.go:586`) mirrors `VerifyLoginCode` (`login.go:252`) case for
   case: attach plus owner flip, keep on the same user, switch of an empty
   guest, and `409` purity on a guest diary, with the pre-check conflict
   changing nothing and the in-transaction race heal re-reading the holder
   and re-checking episodes exactly as the code flow does. The only
   structural difference is the absent code consumption step, which is
   correct because the provider code is single use and already spent.
   Conflict keeps the validated pending (`googleRevisit`, `google.go:569`)
