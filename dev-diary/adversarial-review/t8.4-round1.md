## Findings

### 1. Expired codes never retried keep their plain address forever

| Column | Content |
|---|---|
| Severity | H |
| Where | `internal/identity/login.go:155-176` at the reviewed hash |
| What | A code past its ten minutes whose owner never attempts a verify keeps its plain address in `login_codes.address` indefinitely. Clearing happens only on sight (`closeCode` from `checkCode`), on consume, on retire, and on send failure. No sweep exists, and no later task owns one. This breaks the phase exit criterion that no address past its code life sits in plain text, and it breaks the landed migration comment that the plain address stays only until expiry. No production SELECT reads the column, so the stored value is pure liability. |
| Pin | Throwaway probe `TestRevProbeExpiredUnretriedAddress` (ran, then deleted): request a code, advance the fake clock eleven minutes, read the row without verifying. On the handed hash it reports `address="ghost@example.com" used=0` and fails. With a scratch post-send clearing the same probe passes while every committed `TestLoginCode*` test stays green, which proves the pin tracks this exact behavior. Scratch edit restored afterwards. |
| Mutation | The one-line scratch edit that flips the pin is a post-send `UPDATE login_codes SET address = '' WHERE id = ?`. Removing it (which is exactly the handed code) reintroduces the defect and fails the pin again. |

### 2. Concurrent first-attach for one address answers 500 to the loser

| Column | Content |
|---|---|
| Severity | M |
| Where | `internal/identity/login.go:261-280` (holder read) vs `282-340` (resolve transaction) at the reviewed hash |
| What | The identity holder is read outside the resolve transaction, then the attach inserts inside it. Two devices signing in one fresh address at once both read no holder, both insert, and the loser takes `500 internal_error` from the `UNIQUE (provider, subject)` violation. The transaction rolls back, so the code stays live and tapping verify again heals through the switch path. That retry is the workaround that keeps this an M. |
| Pin | Throwaway probe `TestRevProbeConcurrentFirstAttachLoop` (ran, then deleted): thirty barrier-started pairs of service-level verifies for one fresh address from two sessions. On the handed hash 27 of 30 rounds refuse one device with `identity: resolve login: constraint failed: UNIQUE constraint failed: identities.provider, identities.subject (2067)`. |
| Mutation | The sequential control is the committed `TestLoginVerifySwitchesEmptyGuestToAccount`, which walks attach-then-switch and passes: the refusal appears only under overlap, so the pin tracks the check-then-act window. At code level the defect reappears whenever the holder read sits outside the resolve transaction, which is the handed shape. |

## Observations (not findings)

- No verify or request throttle exists before T8.5. The phase plan
  assigns ceilings to T8.5, which requires T8.4, so landing without
  them follows the plan. Each code still allows six guesses.
- Concurrent wrong tries can lose one attempt increment through a
  read-modify-write race. The practical gain is a small number of
  extra guesses inside a six-try budget that T8.5 further bounds, so
  this stays a note.
- Non-empty but malformed addresses reach Resend and come back as
  500 with the row deleted. Format validation is not in the T8.4 spec,
  and T8.5 owns the abuse ceiling, so this stays a note.
