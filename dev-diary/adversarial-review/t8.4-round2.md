## Finding 2 (round 1 M) is closed

The attach branch catches the insert failure, re-reads the holder
inside the same resolve transaction, and joins it: an empty guest
switches, a guest with episodes gets `ErrDiaryConflict` unless it
chose switch, and a same-user holder falls through to rotation.

- The catch matches no driver error text and no error type. It is
  still narrow enough, because it never swallows a failure. Any
  insert error leads to a re-read inside the transaction. When no
  holder exists the original error returns as a 500, exactly as
  before, so a genuine store fault still surfaces. When a holder
  exists the insert could only have collided on the provider
  subject pair, and joining it is the correct outcome. The worst
  case (a transient fault beside a real holder) joins rather than
  500s, which is the desired semantics anyway.
- Atomicity holds. The consume UPDATE precedes the attach inside
  one transaction, and the conflict return leaves `committed`
  false, so the rollback undoes the consume. The loser keeps a
  live code, matching the sequential 409 purity the committed
  conflict test pins. My race probe proves this on the catch path
  itself: catch-path 409 leaves `used_at` at 0 and the switch
  retry heals.
- Loser semantics equal the sequential path. Empty guest: target
  becomes the holder with `switched = true`. Guest with episodes
  and no switch choice: `ErrDiaryConflict` with nothing consumed.
  With switch: target becomes the holder. Same-user holder: falls
  through to rotation unchanged, matching the sequential
  same-user case which also skips the kind update.
- The success path is untouched: the insert followed by the kind
  update became an if/else-if with identical order and effects.
  The committed concurrency test (10 barrier-started rounds,
  both devices 200 on one account, one identity per round) passes
  repeatedly under `-race`, and my revert mutation proves it
  fails without the catch.
