## What the commit does

The bound job runner moves behind a read write lock in both services and is
captured once per call or attempt, then threaded as a parameter. `retention`
gains `runnerOf` plus `runOn` (the old `run` with a runner parameter) and
`snapshotOf` takes the runner. `privacy` gains `runnerOf` plus `EraseOn` and
`ReEraseOn`, and the sweep calls those variants with its captured runner. The
phase file carries a one line status revert that sits outside `owns` and must
drop before landing.

## Happens-before ruling (explicit)

The fix is sound by inspection. Green runs did not decide this, because the
race never fires locally (see evidence below).

Write edge: the only stores to the shared field are `retention.go:153` and
`privacy.go:182`, each under `mu.Lock`. Read edge: the only loads are the two
`runnerOf` bodies (`retention.go:164`, `privacy.go:193`), each under
`mu.RLock`. Unlock of a write happens before a later read lock on the same
mutex, so every capture synchronizes with the latest completed bind. `grep`
over both packages confirms no other `s.runner` access remains.

No path bypasses the lock. `Sweep`, `ReSweep`, and the `resume` closure all
capture through `runnerOf` exactly once. Every downstream step (`runOn`,
`snapshotOf`, `sweepGuest`, `eraseEpisode`, `finishRecorded`, `retryRecorded`,
`startErasure`, `waitErasure`, `EraseOn`, `ReEraseOn`) takes the runner as a
parameter and never re-reads the field. Resume, retry, and destroy are
covered: resume captures at execution through `runnerOf`, retries thread the
attempt runner into `ReEraseOn`, and no close or destroy path touches the
runner (no such method exists). The HTTP handler uses `Erase`, which captures
once per request. `s.inner` and `s.eraser` are read without the lock but are
written once in `New` before publication and never rebound, so they need no
lock. The allowlist carries its own mutex.

The lock cannot deadlock against the job runner. Each critical section holds
only a pointer store or load. No `keel/job` call and no second lock runs
under `mu`. `BindRunner` releases `mu` before calling the inner bind, so the
two service locks never nest. There is no lock ordering to invert.

One timing note, not a defect. The `resume` closure reads the currently bound
runner at execution time, which matches the pre-fix timing (the old `run`
also read the field at execution). In the restart pattern both runners share
one store, and in the test pattern the old runner is cancelled. `Sweep` now
pins the starting runner in its closure instead of re-reading at execution,
which is strictly more consistent than before. Behavior is preserved.

## Production behavior, hunk by hunk

Every production hunk is justified. The sweep still deletes exactly once and
erasure targets are identical.

- `retention.go` (lock field, locked bind, `runnerOf`, comment): creates the
  happens-before edge. Same pointer stored and returned. No logic change.
- `privacy.go` (same shape): same justification.
- `sweep.go` `Sweep` and `ReSweep`: one capture replaces two reads (call time
  plus execution time) that could disagree across a rebind. Same runner absent
  a rebind.
- `sweep.go` `resume` closure: captures at execution through the lock, same
  timing as the old `run` read, now synchronized.
- `run` to `runOn`: parameter threading only. `plan`, `expired`, `episodes`,
  `sweepGuest`, `eraseEpisode`, `waitErasure`, `deleteStrays`,
  `deleteGuestRows`, and `publish` are untouched.
- `erase.go` wrappers plus `EraseOn` and `ReEraseOn`: inventory, target list,
  `Inspect`, and `Start` call order are byte for byte the old logic with the
  runner from the parameter. Targets are identical, so deletes still land
  exactly once with idempotent retry from recorded ids.
- Edge noted, not a finding. The nil runner check now runs before the empty
  argument check in the `On` variants. Both faults wrap the same `ErrInvalid`
  sentinel, so callers branching with `errors.Is` see no change. Only the
  message in the double fault case differs.
